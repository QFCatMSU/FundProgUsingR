3 Debugging your code

One of the most powerful debugging tools in any programming language, and a staple of most professional programmers, is the breakpoint.  Breakpoints allows you to pause the execution of your script at a specific line or command.  While paused, you can look at Variables as they are at that moment in the script’s execution, enter commands in the Console, or step through your script’s execution. This is a very useful tool for tracking down hard-to-find problems in your script.

 

The implementation of breakpoints in R was historically far less robust than most programming languages. However, in February 2026, Positron added breakpoints – marking the first time an R development environment effectively implemented breakpoints (RStudio has breakpoints, but they were not well implemented).

3.1 Issues with breakpoints in Positron

Breakpoints were first introduced to Positron in February 2026 and, while they work, there are still some obvious bugs and quirks. Positron knows about the issues and I would expect them to be fixed by mid-2027. Until then, I will mention the bugs, how things should work, and they currently work.

 

Here are the bugs (and a bit of self-promotion, too):

  • https://github.com/posit-dev/positron/issues/15532

  • https://github.com/posit-dev/positron/issues/15533

4 Setting up a breakpoint

A breakpoint is like a pause button in the execution your script.  In Positron, you set a breakpoint by clicking to the left of the line number – this space is called the gutter area.  A gray-outlined dot is initially put in the gutter area (line 4) – indicating that this is an unverified breakpoint. Once the script is sourced and the code in the line is verified, the dot becomes red (line 8). Note: Clicking on the breakpoint dot removes the breakpoint.

When you Source your code, the script will execute up to, but not including, the line with the breakpoint.  Your script is now paused at the line with a breakpoint, and you are in debug mode, which R calls Browse mode (Figure 2).

 

Note: A breakpoint only works when you Source your script.  It will not work if you use Control-Enter to execute individual lines of code.

4.1 Debug Mode

There are 4 things in Positron that indicate you are in debug mode:

  1. A hollow arrow appears at the code line the script is paused at. The arrow shows you the line that will be executed next (i.e., the script is paused right before the line of code)

  2. Floating debug controls appear in file tab area

  3. The Console indicates it is in browse mode with Browse[1]>

  4. The Run and Debug tab appears on the left side

    • this tab has more advanced debugging tools that we will not get into in this lesson

6 Moving through code in debug (browse) mode

When your script arrives at a breakpoint (Figure 2), a floating control bar with six buttons appears.

 

In order, the control buttons are:

1) Continue: unpauses the execution of the script (like hitting the Play button when a video is paused)

2) Step Over: executes the command at the arrow (in RStudio, this is called Next)

3) Step Into: moves into a function

  • if the command has no function, Step Into acts like Step Over

4) Step Out: completes a for loop or function and pauses the script at the next line

  • if not in a for loop or function, Step Out acts like Continue
  • BUG: if the breakpoint is in a for loop or function, Step Out will exit but not pause at the next line
    • this is a pretty nasty bug because it creates very confusing scenarios!

5) Restart: Stops execution and restarts R

  • BUG: broken – use Restart in Console (Figure 3), which performs the same function

6) Disconnect: quits the script (no more code is executed)

6.1 Do not use Source in Debug Mode

When in debug mode you should only use the six buttons to control the flow of your script.  Clicking Source while in debug mode will put you into multiple debug modes at once. This is not something you want to do at this point. Extension: Clicking Source in debug mode.

6.2 Disconnect

Clicking Disconnect will take R out of debug mode and end the execution of the script.  In other words, no more commands in the script will be executed and all the components of debug mode (Figure 2) will go away.

 

When you click Disconnect, Q is put in the Console. Q is the command to quit debug mode. You could directly type Q instead of clicking Disconnect.

6.6 Moving out of a for loop

If you are in a for loop with thousands of cycle then you do not want to keep clicking Continue until you are out of the for loop.

 

There are three ways to get out of the for loop with one click:

  1. Click Step Out – this should complete the for loop and pause execution at the next command after the for loop (line 29)

    • BUG: Step Out will not pause execution at the next command

    • Bug fix: add breakpoint right after the for loop on line 29

  2. Click Disconnect – this will end debug mode and stop the script but leave everything in Variables

  3. Click Restart in Console tab (Figure 8) – this will end debug mode, restart the R session, and clean out Variables

6.6.1 Restart control bug

The Restart button in the debug controls will also restart the R session and clean out Variables, but breakpoints will not work after this (this is a bug in Positron). If you click Restart in the debug controls, then you will need to either click Restart in the Console tab or close out and reopen Positron.

6.7.1 Step Over and Next

Many debuggers choose to call the Step Over control Next. Step Over and Next both functionally do the same thing but they take a different perspective.

 

Both tell the debugger to run the next command fully. But Step Over is explicitly saying to run all functions within the command (i.e., Step Over the functions), which could be thought of as subcommands. This is to contrast with Step In, which explicitly tells the debugger to go inside the functions (i.e., Step In the function). I personally feel like the term Next is more intuitive.

7 Debugging inside a for loop

In lesson script:

  • Click Step Over until you get to line 22
22 for(i in 1:length(sunsetTimes))

When the arrow gets to a for loop, Positron will highlight the whole for loop:

7.1  Execute for loop initialization

Clicking Step Over again executes the initialization command for the for loop:

for(i in 1:length(sunsetTimes))

In this initialization command:

  • the variable i is set to 1 (i will be put in Variables)

  • a rule is given for how i changes each time the for loop cycles (i.e., i increases by 1)

  • the cycles end when i is equal to the length of sunsetTime

 

The initialization command of a for loop executes once whereas everything inside the for loop executes once per cycle of the for loop.

 

After the initialization command is executed, Step Over will move to the commands inside the for loop codeblock:

If you keep clicking Step Over then debug mode will go through each command in the for loop for each cycle of the for loop (that could take a lot of time!). If you click Continue, debug mode will go to the next breakpoint or the end of script if there are no more breakpoints.

7.2 Step Out of the for loop

Note: The for loop and Step Out bug only occurs when you stop at a breakpoint in the for loop, which is not true in this case.

 

If you are inside a for loop and want to finish executing the whole for loop (i.e., complete every cycle of the loop), you can click Step Out.  This will execute the rest of the for loop and put the control at the next command (in this case, the if-else structure).

7.3 Conditional breakpoints

Debugging a for loop can be quite tricky if it is cycling thousands (or millions) of times. You likely do not want to pause the execution of your code every time the for loop cycle. Instead, you want to pause execution when an event occurs. To do this, we add a condition to the breakpoint. Conditional breakpoint only activate in debug mode when the condition is met – this is one of the most powerful debugging tools in programming.

7.3.1 Pause for loop at a specific cycle

In lesson script:

  • Click Disconnect

  • Remove all previous breakpoints (click Run -> Remove All Breakpoints…)

  • Right-click in the gutter area on line 25 (Figure 16)

  • Choose Add Conditional Breakpoint…

  • Choose Expression (default choice) and put in i==200

  • Click enter

With the conditional breakpoint on line 25, the script will pause on the 200th cycle of the for loop:

7.3.2 Expressions are conditional statements

The Expression for the breakpoint works just like a conditional statement in an if() and uses the same logic.

  • i>200 # i greater than 200

  • i<=200 # i less than or equal to 200

  • i==200 & j==300 # i equal to 200 and j equal to 300 (assuming there is a j)

7.3.3 Pause for loop based on variable

This time we will pause the script inside the for loop when a variable meets a condition (sunsetTimes[i] == 2000)

 

In lesson script:

  • Click Disconnect

  • Right-click in the gutter area on line 25

  • Choose Edit Breakpoint…

  • Choose Expression and put in sunsetTimes[i] == 2000

  • Click enter

 

The script will pause on the 141st cycle of the for loop, which represents the first day that sunset is at exactly 8:00pm (2000 hours)

8 If-else statements

In lesson script:

  • Remove all previous breakpoints (click Run -> Remove All Breakpoints…)

  • Add a breakpoint on line 29

29 if(testCommand3 == 1) # FALSE

Similar to the initialization of for loops, the conditional statement inside the parentheses of if-else statements is a command.  The command outputs a Boolean (TRUE/FALSE) value that is used to determined if the codeblock gets executed.

 

When you set a breakpoint at the if() line, the whole if-else is highlighted in Positron when the code is stopped at the line. 

As you click Step Over, the control (arrow) will either:

  • move to the next conditional statement (if the current conditional statement is FALSE)

  • move inside the codeblock (if the current conditional statement is TRUE)

 

The following lines are not executed in an if-else structure and will be skipped over in debug mode:

  • codeblocks attached to FALSE conditional statements

  • else statements that were preceded by a TRUE conditional statement

    • the codeblock attached to these else statements will also not be executed

8.1 Quirks with debugging if-else structures

If you put a breakpoint on an else if or else statement (lines 33, 37, 41, and 45 in Figure 17) , that breakpoint will either not work or move to the if line (line 29 in Figure 17). Breakpoints inside codeblocks attached to else if or else statements will work (assuming the codeblock gets executed).

 

If you put a breakpoint on line 29 in Figure 17 and click Source, Step Over will go from line 29 to 33 to 37 to 39. But only line 39 will get highlighted making it hard to see the interim steps. This seems like a bug.

12 Extension: Modifying breakpoints in debug mode

Breakpoints can be added and removed at any time, even when you are already in debug mode. However, breakpoints modified in debug mode will not work until the next time the script is Sourced. You will see an the outlined gray dot indicating the breakpoint is not active.

 

If you remove a breakpoint in debug mode, the red dot will disappear but the breakpoint remains in effect until you exit debug mode.
